# 旅行行程规划页面审视

## 范围

- 页面：网页版 `http://127.0.0.1:4177/?v=passenger-stations-1`
- 用户目标：从多个中国城市中选择路线，并得到一份可以阅读、分享、执行的旅行计划。
- 截图：
  - `01-start.png`：初始页面
  - `02-route-one-segment.png`：北京 -> 郑州
  - `03-route-two-segments-viewport.png`：北京 -> 郑州 -> 武汉

## 步骤健康度

1. 初始页面：健康。地图、搜索、交通方式、汇总信息都清楚，但用户只能开始选点，还看不到最终会得到什么类型的方案。
2. 搜索并选择出发城市：基本健康。搜索结果可用，但城市和区县结果视觉层级接近，容易误选。
3. 形成多城市路线：中等。路线链路、距离、时长能生成，但仍是路线段计算器，不是完整旅行行程。
4. 查看食行记：有价值，但未并入行程。文章中的“第 N 天”来自原始内容系列，不是用户本次旅行天数。
5. 导出：偏弱。导出为结构化 JSON，适合二次开发，不适合普通旅行用户阅读、收藏或转发。

## 主要缺口

1. 导出内容需要从数据文件升级为旅行指南。建议提供 Markdown/HTML/PDF 三类阅读型导出，包含封面摘要、路线总览、每日安排、交通段、城市亮点、美食文章、注意事项和可分享链接。
2. 需要按天规划。用户需要“第 1 天 北京，第 2 天 郑州，第 3 天 武汉”这种日程视角，并支持每城停留天数、当天到达/离开时间、是否过夜。
3. 缺少城市内行程。当前有区县、景点、车站、地铁、食行记，但没有自动组合为上午/下午/晚上，也没有游玩耗时、开放时间、交通耗时和餐饮位置。
4. 缺少住宿和落脚点。真实旅行会围绕酒店/车站/景点之间移动，至少需要“推荐住宿区域”“到达站点”“离开站点”“当晚住哪座城市”。
5. 缺少可行性校验。当前总时长只算跨城交通，没有提示“当天跨城后还剩多少游玩时间”“是否太赶”“是否需要拆成两天”。
6. 搜索结果需要更明确地区分城市和区县。建议把“城市”置顶并加明显标签，区县折叠到城市下，避免误点。
7. 交通信息需要更接近真实用户表达。当前是估算距离/时长，建议补充“估算，不代表具体车次”“建议查询实际班次”，并预留车站、出发时间、到达时间字段。
8. 需要保存/恢复/分享。普通用户会希望稍后继续编辑，或者把路线发给同行者；只下载 JSON 不够。
9. 需要移动端操作优化。左侧面板内容变长后阅读和地图操作会互相挤压，应考虑“地图/行程”两个视图或底部抽屉。

## 推荐优先级

P0：导出旅行指南、按天规划、可行性校验。

P1：城市内上午/下午/晚上安排、食行记并入每日推荐、搜索结果分层。

P2：住宿区域、预算/强度偏好、保存分享、移动端双视图。
